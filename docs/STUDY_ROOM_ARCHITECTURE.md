## 二、数据库模型

### 核心表结构

| 表名 | 用途 |
|------|------|
| `study_rooms` | 房间信息（名称、密码、创建者、状态） |
| `room_members` | 成员信息（用户名、番茄数、学习时长） |
| `daily_room_records` | 每日学习统计（归档用） |

### 关键字段

**study_rooms 表：**
- `id`: 主键
- `room_code`: 房间号（唯一标识）
- `room_name`: 房间名称
- `password`: 房间密码（可为空）
- `is_active`: 是否活跃
- `created_by`: 创建者用户名
- `created_at`: 创建时间

**room_members 表：**
- `id`: 主键
- `room_id`: 关联房间
- `username`: 用户名
- `tomato_count`: 完成的番茄数
- `focus_duration`: 专注时长（秒）
- `join_time`: 加入时间
- `is_online`: 是否在线
- `last_heartbeat`: 最后心跳时间

## 三、核心功能流程

### 1. 创建房间

```
用户输入房间名/密码 → 检查房间号是否存在 
                   → 创建房间记录 
                   → 自动以创建者身份加入
```

**🎲 随机名称（v4.5.10 起，v4.5.11 扩充）**：房间名输入框旁新增 🎲 按钮，一键生成**与当前时间相关的有设计感的随机名**（可多次点击换新），来源 `src/utils/roomName.ts` 的 `generateRoomName()`：
- **时段意象**：按当前小时分 7 段、每段 6 个意象词（晨光/破晓/朝阳/微曦/初晴/启明、书页/启程/窗台/晨读/专注/青空、正午/日悬/暖阳/晌午/烈日/高照、午后/余晖/慢煮/茶歇/慵懒/暖窗、黄昏/暮色/归途/晚霞/落照/倦鸟、夜读/灯下/萤火/星夜/晚风/月下、静夜/星火/守夜/子时/深蓝/零点），名字与当下时间有关、不无意义；
- **学习名词池**：37 个（番茄/书桌/笔尖/心流/灯塔/岛屿/树洞/穹顶/花园/时光/窗棂/钟摆/砚台/灯芯/藤蔓/山径/溪谷/云影/屋檐/烛光/沙漏/钥匙/诗行/木屋/风铃/晨露/麦田/星图/炉火/纸船 + 桃花源/九重塔/千纸鹤/月亮船/时光机/萤火虫/忘忧草）；
- **格式**：`时段意象 + 名词 + 两位数编号`（10-99），组合空间约 14 万种，示例：`暮色书桌 23`、`夜读萤火 41`、`月下纸船 07`、`深蓝桃花源 52`。

**同步听歌"使用说明"（v4.5.11）**：同步听歌卡片新增可展开的 📖 使用说明（`syncInfoOpen` 折叠状态），未开启同步时也能先了解机制，重点告知用户：① 房间由 DJ 控制播放、其他人跟随；② 缺歌自动 P2P 传歌（边下边播/全员就绪统一播两种模式）；③ **开启同步即代表同意把本地歌曲共享给房间内缺歌的人**（仅房间内点对点传输，不上传公开服务器）；④ 下载的歌曲保存到本地音乐库并打上来源标签（DJ 名字），可随时删除。

### 2. 加入房间

```
输入房间号+密码 → 验证房间是否存在/密码正确 
               → 检查是否已在其他房间 
               → 添加成员记录
```

### 3. 学习数据同步

```
番茄钟完成 → 累加本地计数 → IPC 发送到主进程 
          → 更新本地数据库 
          → 同步到云端 Supabase
```

### 4. 实时数据更新

```
前端定时轮询(每5秒) → 获取房间所有成员最新数据 
                   → 刷新 UI 排行榜
```

## 七、心跳机制（已实现）

### 设计理念

采用**去中心化检测**方式：每个客户端心跳时都会检查所有房间和成员的状态，而不是依赖单独的清理进程。

### 心跳触发时机

| 时机 | 当前实现 | 说明 |
|------|----------|------|
| 进入房间 | ✅ 已实现 | `startHeartbeat()` 立即执行一次 |
| 退出房间 | ❌ 未实现 | 需要在离开前执行最后的心跳 |
| 定时心跳 | ✅ 已实现 | 每 5 分钟执行一次 |

### 心跳检查流程

```
updateOnlineStatus(roomId):
  1. 更新当前用户:
     - last_active = now
     - is_online = true
     
  2. 检查所有成员超时:
     - 获取所有自习室的所有成员
     - 如果 last_active > 11分钟 且 is_online = true
     - 批量更新为 is_online = false
     
  3. 检查空房间:
     - 获取所有 is_active = true 的房间
     - 如果房间无在线成员
     - 更新为 is_active = false
```

### 超时阈值

- **心跳间隔**：5 分钟
- **超时阈值**：11 分钟（心跳间隔 × 2 + 1分钟宽限）

### 相关 IPC 接口

```javascript
// 发送心跳并触发检查
window.electronAPI.studyRoomUpdateStatus(roomId)
```

## 十二、心跳机制（已完善）

### 设计理念

采用**去中心化检测**方式：每个客户端心跳时都会检查所有房间和成员的状态。

### 心跳触发时机

| 时机 | 状态 | 说明 |
|------|------|------|
| 进入房间 | ✅ | `startHeartbeat()` 立即执行一次 |
| 退出房间 | ✅ | 调用 `checkRoomStatus()` 检查房间状态 |
| 定时心跳 | ✅ | 每 5 分钟执行一次 |

### 心跳检查流程

**updateOnlineStatus（心跳）**：
1. 更新当前用户 `is_online = true`
2. 检查所有成员，超时（>11分钟）的标记离线
3. 检查空房间，标记 `is_active = false`

**checkRoomStatus（只检查）**：
1. 检查指定房间的成员超时
2. 检查房间是否需要下线
3. **不更新当前用户的在线状态**

### 超时阈值

- **心跳间隔**：5 分钟
- **超时阈值**：11 分钟

### 2. 房间权限模型（v4.4.1 起）

| 能力 | 说明 |
|------|------|
| 房主（owner_id） | 唯一创建者；可删除房间、切换公开/私密、设置/清除密码 |
| 公开房间 | 出现在 `GET /api/v1/rooms` 列表，任何人可加入（无密码） |
| 私密房间 | 不出现在公开列表，只能通过 ID 加入；可另设密码（ID+密码） |
| 密码规则 | 设置非空密码 → 自动转私密；设为公开 → 自动清空密码（服务器强制） |

### 3. 核心流程

**创建**：名称 + 描述 + 隐私（公开 / 私密 / 私密+密码）→ `room:create`（WS 请求-响应）
**加入（ID）**：先 `GET /rooms/:id` 查详情 → 若 `has_password` 则弹出密码输入 → `room:join` 带密码
**在线成员**：join 后服务器广播 `room:members`；客户端若尚未进入房间视图则暂存到
`pendingMembers`，进入后应用（修复"在线成员显示为空"）；`presence:update` 推送
`member_status` 实时更新专注状态
**房主管理**：公开/私密切换、密码设置 → `PUT /api/v1/rooms/:id`（仅房主 200，否则 403）
**删除**：`DELETE /api/v1/rooms/:id`（仅房主）

### 4. 同步听歌（v4.4.0 起）

- 音频本地播放，服务器仅转发控制动作 + `timestamp_server` 时间戳
- DJ 模式：`music:request_dj` → `music:dj_changed`（比对 `dj_user_id` 与当前用户判断身份）
- 听众端：收到 `music:state` 后 `position = position_ms + (Date.now() - timestamp_server)` 校准跟播
- 事件统一由 `MusicPlayer.vue` 监听 `ws-event` 转发到 `music.ts` 的 `handleSyncWsEvent`

### 5. ★ 队列 × 同步：一个必须知道的耦合事实

音乐库引入「播放集合（队列）」后，出现了**第二种"位置"**，它与已同步的播放位置
是两回事：

| 位置概念 | 现状 | 权威方 |
|---------|------|--------|
| **播放位置** `positionMs` | ✅ 已同步（`music:state` / `music:sync_state`，含 `timestamp_server` / `djServerTime` 时钟校准） | DJ |
| **队列顺序**（第 3/12 首、下一首是谁） | ❌ **完全没同步** | **只有 DJ 有** |
| 听众本地队列 | 是听众**自己的**库，与 DJ 无关 | 听众自己 |

`music:sync_state` 的载荷是：

```
{ songId, playing, positionMs, volume, transferMode, djServerTime }
```

**只有"当前歌"，没有队列。** `playSet`（前端）与 Rust 的 `active_list` 都只存在于
DJ 本机；`get_next_song` 按 `active_list` 取模/随机决定下一首，**这个决定过程
从不广播**。听众每次只能被动接受一个 `songId`。

#### 由此得出的两条结论

1. **听众端不能展示任何"队列 / 下一首"** —— 它算出来的必然与 DJ 实际要播的无关。
   （已修：`MusicPlayer.vue` 的 `playlistBtnTitle` 在 `controlsDisabled` 时改显示
   `由 <DJ名> 控制`；单测覆盖本机 / 听众 / DJ 三种身份。）
2. **提前传歌（预取）在当前协议下做不到** —— 缺的正是"DJ 的队列"这份数据。
   见下节。

> ⚠️ 顺带澄清一个易混点：`music:playlist_updated` **不是"同步歌单"**。
> 听众端收到它只做 `requestPlaylist()` —— 重新读**自己本地**的歌单，
> 语义是"你的本地库变了，重读一下"，不是"DJ 的歌单是这样"。

### 6. 待设计：同步队列 + 预取（"分支预测"）

**设计决定（已拍板，未实施）**：

- **只预取下一首**（深度 = 1，不做深预取）；
- **只在「当前歌传输完毕并开始播放之后」才启动预取**。

**第二条是关键**：当前歌传完之后带宽本来就闲着，此时预取**不可能与当前歌竞争带宽**，
于是**根本不需要**再设计优先级、限速、"当前歌未就绪时暂停预取"那一套调度机制。
这是用**时序**而不是**调度**来消除竞争 —— 更简单，也更可靠。

实测数据支持这个时序是可行的（见 §7 的工具）：
中转路径吞吐 **≈0.28 MB/s（≈2.2 Mbps，已顶到服务器 2 Mbps 带宽上限）**，
一首 5MB 的歌走中转约需 **18 秒**；而当前歌的播放时长通常 3 分钟以上
→ **预取有 10 倍以上的时间余量**。

**预取应当优先走 P2P。** 实测 P2P 直连 **20.95 Mbps，比中转快约 10.5×** ——
同样 3.3MB 的歌，P2P 约 **1.3 秒**、中转约 **14 秒**。
所以预取不仅是"来得及"，在 P2P 可用时几乎瞬间完成；
只有 P2P 打不通（对称 NAT 等）时才回退中转。
这也意味着**预取不该占用服务器那 2 Mbps** —— 那是当前歌下载的救命带宽。

**先分清两个容易混的概念**：

| | 现有 `wait_all` | 预取 |
|---|---|---|
| 目标 | 保证**当前**这首歌全员就绪才播 | **下一首**提前到位 |
| 时序 | **阻塞**当前播放 | 不阻塞，后台 |
| 现状 | 已实现 | **零**（全项目搜不到任何 prefetch） |

`wait_all` 是**阻塞**，不是预取，两者不能互相替代。
（反过来：`wait_all` 下预取收益最大 —— 它把"等待"提前完成了。）

**为什么"分支预测"这个比喻是准确的**

| CPU | 这里 |
|---|---|
| 预测执行 | 预取下一首 |
| 预测正确 → 流水线不空 | 切歌瞬间可播，不再"获取歌曲中 x%" |
| **预测错误 → 清空流水线** | **DJ 跳歌 → 预取白费，必须能取消** |
| 预测深度有限 | **深度 = 1**（用户已拍板） |

**仍需处理的情况**：

| 情况 | 处理 |
|------|------|
| **预测错误**：DJ 跳歌 / 改队列 | 取消在途预取，改预取新的"下一首"。深度=1 让浪费有界 |
| DJ 跳到的歌恰好是已预取的那首 | 直接命中，无需传输（这正是收益） |
| 跳到的歌本地没有且没预取 | 回到"等待传输"；此时**必须暂停预取**，把带宽让给当前歌 |
| 单曲循环 / 队列只有 1 首 | `next == current` → 跳过预取 |
| 听众本地已有这首歌 | 无需传输（先查本地库） |
| 听众晚加入 | 只预取"从当前 index 往后"的，深度按剩余队列长度截断 |
| 缓存一致性 | 预取文件必须落在与按需下载**同一个**目录，否则出现重复文件（`music:song_missing` 那套判定曾误判过） |

**需要的最小协议改动**：DJ 广播"下一首是什么"。
**只需 `next_song_id` 一个字段**（不必广播整个队列）—— 这既满足预取需求，
又不暴露 DJ 的完整歌单，且没有带宽风险。
等这条跑稳，再考虑是否广播完整队列（那是为了 UI 能诚实展示"DJ 的队列"，
与预取是两件独立的事）。

**先不做**：P2P 并发放大、分片速率整形 —— 深度=1 + 空闲时预取已把风险压到很低。

#### ✅ 多听众传歌去重 + 中途加入听众的残缺隐患（v4.11，2026-10 已上线）

**背景**：`EXTERNAL-INTERFACES.md` 规定服务器"**可同时转发给房间内所有缺歌者，减少重复传输**"，
但实测**未实现**：1 个 DJ → 3 个听众时，DJ 被要求服务 **3 次**（上行放大 3×）。
而 DJ 通常在国内家庭宽带上行，这一放大是实打实的代价。

**更严重的相邻隐患（做去重时才暴露）**：**中途加入的听众**会拿到残缺文件。
实测：听众 A 先请求并开始下载，**5 秒后** B 才请求 →

```
B 只收到 12/27 片，序号 15..26（缺头部 0..14）
却收到了 transfer_done（"已完成"）
→ 客户端会拼出残缺文件，只能靠 music_finalize_song 的分片校验发现再走 from_chunk 续传自愈
```

根因：`handle_music_request_song` 把新请求者直接加进 `uids`，但**前半段分片已经转发过了**；
而该轮结束的 `transfer_done` 会 `pop` 掉整个请求状态并通知全体。

**实现（v4.11，"轮次"模型）**：

- 一轮 = 一次 `music:song_requested` + 持有者随后回传的一串分片；该轮分片扇出给本轮全体 → **持有者只上行一份**。
- 只有"本轮**尚未回传任何分片**（`chunks == 0`）且路径（p2p）与起点（from_chunk）一致"时才允许并入（真去重）。
- **已开始回传才来的听众 → 排队（`pending`）**，本轮结束后就地提升为下一轮并向持有者重新发起。
  不能并入（会缺头），也不能让它从当前进度续传（`from_chunk` 的语义是"我已保存 N 片"，新听众是 0 片）。
- **带 `p2p` 的请求必须独立成轮**：P2P 是点对点 DataChannel，无法扇出，并进别人的轮会一直收不到数据。
- 同一时刻只允许一轮在飞 —— 并发多轮会互相串流，且任一轮的 `transfer_done` 会丢弃另一轮的分片。
- 同一听众重复请求（客户端 12s×3 重试）：有进展即忽略，停滞超过 `REREQUEST_STALL_SEC` 才重新触发。

**两个必须记住的坑**（实现时都踩到了）：

1. `handle_music_offer_song` 里**必须递增 `req["chunks"]`** —— 否则"本轮尚未开始"的判据恒为真，
   任何中途加入者都会被并进来并收到残缺数据（实测就是卡在这里：B 仍只拿到 12/27）。
2. `_forward_transfer_result` **不能再无条件 `pop`** —— 否则排队者既拿不到分片、也没有下一轮，
   会被永久卡住（直到 30s 超时）。

**验证（经真实服务器）**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 3 个听众同时缺歌 · DJ 服务次数 | 3（上行放大 3×） | **1** |
| 3 个听众完整性 | 3/3 逐字节一致 | 3/3 逐字节一致（去重未牺牲正确性） |
| 中途加入听众 B | ❌ 只拿到 12/27 片 | ✅ **27/27 逐字节一致** |
| 全套回归 | — | **38 通过 / 0 失败 / 8 观察 / 0 疑似缺陷** |

#### ✅ `wait_all` 协调消息曾从未触发 —— 已定位并修复（2026-10，主部门）

**现象**：`wait_all` 模式下 `music:song_waiting` / `music:songs_ready` **一条都收不到**。

**用户可见影响**（按 `src/stores/music.ts` 的设计意图）：
`song_waiting` 的意图是让 DJ **暂停等人**（`handleSongWaiting` → `togglePlay()`）、
`songs_ready` 是让 DJ **从头统一起播**（`handleSongsReady` → `togglePlay()` + `seek(0)`）。
两者都不来 → **`wait_all` 静默退化成 `immediate`**：DJ 不等任何人、不从头统一起播。

##### 定位过程与一个必须记住的教训

一开始我以为是"服务器没实现"，**并据此在留言区给服务器部门报了 bug —— 那是错的**。
真正的定位分了三步，每步都推翻了上一步的猜测：

| 步骤 | 结论 |
|---|---|
| 1. A/B 对照（DJ 传歌期间是否周期广播） | 两组都 0 条 → 一度以为是"偶然触发" |
| 2. 修掉**我自己工具**的两个 bug | ① DJ 替身漏传 `transfer_mode`，每次广播把服务端房间的 `wait_all` **覆盖回 `immediate`**（真实应用 `music.ts:515` 是带的）；② 周期广播放在"发送分片"循环里，而那个循环**只花 ~20ms**，5s 间隔根本没机会触发 |
| 3. **服务器侧插桩**（`docker logs` 时间戳） | 拿到铁证 ↓ |

**铁证（线上插桩日志）**：

```
12:54:49.506  [DIAG_REQ]  uids=['5e75cc…']      ← 请求已落库，房间 mode=wait_all
                 ⋯ 11.6 秒空窗，handle_music_sync_state 一次都没被调用 ⋯
12:55:01.126  [DIAG_END]  popped=['5e75cc…']    ← 传输结束，请求被 pop
12:55:01.126  [WAITALL_DIAG] uids=None          ← 直到 pop 之后才被调用
```

同时把线上那个函数**单独 import 出来做单元测试**，证明它自身逻辑完全正常
（有缺歌者 → 广播 `song_waiting`；请求清空 → 广播 `songs_ready`）。

→ **函数是对的，问题是它从没在条件满足时被调用。**

##### 根因

`_maybe_wait_all()` 只有两个调用点，现实中**都不会命中**：

| 调用点 | 为什么不命中 |
|---|---|
| `handle_music_sync_state`（DJ 广播状态） | 唯一能发出 `song_waiting` 的路径，但请求挂起的那 11.6 秒里它**一次都没被调用**：持有者发送循环 ~20ms 就结束，而服务器以 2Mbps 中转要 11.6s，所以"传歌期间每 5s 广播"不存在 |
| `_forward_transfer_result`（传输结束） | 它**先 `pop` 掉** `song_requests[song_id]` 再调用 → `missing` 恒为 `False` |

而本该触发它的 `handle_music_request_song`（听众请求缺歌）**没有调用它**。

在 `handle_music_request_song` 记录请求者之后、**`with _lock:` 之外**
（`_maybe_wait_all` 内部自己要拿 `_lock`，放进去会死锁）补一行：

```python
_maybe_wait_all(room_id, song_id)
```
